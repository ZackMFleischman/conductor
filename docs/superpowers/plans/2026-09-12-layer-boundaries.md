# Separate ticketing, workflow policy, and agent coordination

**Goal:** Make the tracker useful by itself; add review/planning policy and managed teams independently.
**Design approval:** User approved the three-layer design in this conversation and requested a small plan, independent review, then implementation.
**Architecture:** One Go executable, one local SQLite store, existing CLI and transactional mutations. Internal functions separate responsibilities; no plugin framework, daemon, hooks, new portal work, or case study.
**Context:** Extends [the runtime plan](2026-09-12-team-runtime.md) and [workflow spec](../specs/2026-09-12-conductor-team-workflow.md); this document supersedes their coupling of dependencies/acceptance to workflow opt-in.

## Boundaries and contracts

- Foundation owns ticket descriptions, kind/parent, dependency graph, assignment, claims, block/release, result submissions, attributed accept/reject evidence, append-only problem reports, and ordinary revision/history. Existing Markdown descriptions/links stay intact; new checklist/artifact UI functionality remains out of scope.
- Policy owns optional preparation/authorization, critiques/dispositions, validation requirements and retrospective scheduling deferrals. Foundation evidence records what happened; policy decides whether a transition is allowed.
- Coordination owns runs, roles, native-host observations, capacity and managed assignment restrictions. Plain sessions never require a team. Agent skills select the workflow, with foundation tracking as the default for registered projects.
- Universal acquisition checks run in the same SQLite transaction: live session, revision, assignment, no competing claim, dependency completion. Policy and coordination checks may add restrictions, never bypass these checks. No cached eligibility used for writes.
- A small concrete dispatcher in `internal/core/transitions.go` calls foundation, optional-policy and optional-team checks using the existing `*sql.Conn`. No dynamic registration, framework or service split. Result authority/evidence checks remain explicit for accept/reject; do not force every command through a generic state machine.
- New plain tickets default to ready and permit a live agent or explicit human to accept/reject with attributable evidence. Existing v1 tickets retain an explicit legacy-human acceptance restriction after migration; do not silently relax existing gates. New configured tickets retain their policy snapshot. All new optional fields use `omitempty` where needed to preserve v1 request hashes.
- Planning policy works without a team: delegated preparation/authorization uses a live session and the standing grant recorded by explicit human `workflow configure` and inherited ticket policy. With any non-stopped team run these operations additionally require its current coordinator token and a usable run state; stopping/released runs require reconciliation and cannot fall back to standalone authority. Policy changes still require explicit user authority. A stopped team cannot supply coordinator authority, and its historical child sessions cannot become standalone workers. Skills must not manufacture a grant or human approval.
- Managed child claims enforce role=worker, exact launch ticket, acknowledged active host/session, usable run, and one implementation attempt per session, including release/reclaim of the same ticket. Classify pending launches by stable identity before session registration as well as registered/historical child sessions, so an unregistered child cannot fall through as plain. Ordinary sessions keep their normal standalone lifecycle. Readiness is rechecked at acquisition; already-owned work can checkpoint/release during shutdown. Validator launches can reference review tickets without matching their implementer assignment.

Minimal parallel contract: L2 supplies `CheckTeamClaimTx(ctx context.Context, c *sql.Conn, projectID, ticketID, sessionID string) error`, which returns nil only for an ordinary session or an eligible managed worker; root/L1 calls it inside acquisition. L1 supplies `CheckTicketDependenciesTx(ctx context.Context, c *sql.Conn, projectID, ticketID string) error`. `CheckWorkflowEligibilityTx` remains the optional-policy adapter and returns nil for no planning policy; dependencies move out of it. Root composes these concrete checks in `CheckTicketClaimTx(ctx context.Context, c *sql.Conn, projectID, ticketID, sessionID string) error`. L2 may call the dependency and workflow helpers for worker launch, but cannot change foundation files. Existing team table layout remains L2-owned and unchanged by L1.

## Migration and compatibility

- Ship schema v3: keep the existing v1-to-v2 migration intact and add v2-to-v3. Use an explicit ordered migration list so opening v2 does not replay v2 creation SQL. Fresh databases traverse the same path; writable opens migrate, read-only opens never do.
- New foundation tables hold metadata/dependencies, version/submission and decision evidence for all tickets. Copy existing optional workflow data into them; retain only policy-specific fields in workflow tables. There must be one authoritative copy of each field, with `ticket show` exposing foundation data even when workflow is absent.
- Preserve UUIDs, display keys, claims, assignments, request journal hashes/results, problem/retrospective links, submission evidence, policy snapshots and approval state. Existing legacy tickets retain human validation through migrated policy, without requiring planning or team setup.
- Keep consistent pre-migration SQLite backups, rollback on error and foreign-key verification. Prove both v1-to-v3 and populated v2-to-v3, including replay of previously successful v1 AND v2 ticket commands. Narrow legacy hash compatibility may recognize only historical ticket payload shapes with omitted versus empty Commit/Validation; do not rewrite journal hashes, drop nonempty fields or accept genuinely changed payloads. Test conflicting changed payloads and read-only opens of v1/v2/v3. No incomplete candidate touches the live registry; stop old clients before installation/migration.
- Preserve current CLI commands where semantics remain valid; extend existing `ticket edit`, `block`, `unblock`, `accept`, `reject` to foundation use. Plain unblock returns ready subject to dependencies at claim. Structured evidence distinguishes accepted versus rejected results and records actor/source commit/criteria/checks when supplied; a policy may require those fields. Rejection must not require passing checks.
- Retrospective analysis can consume problem reports and create/link ordinary foundation improvement tickets without enabling the planning workflow; configured projects still produce gated drafts. Milestone deferral is an optional additional acquisition restriction. Standalone release requires live-session attribution, reason/evidence and authorized scope; with a non-stopped team require the current usable coordinator. Milestone release returns plain tickets to ready and invalidates gated tickets back to draft. No automatic team startup or policy opt-in.

## Acceptance and review

For each changed behavior, reproduce the missing guarantee with a failing focused test, implement, and rerun it. Then independently review the combined changes and test:

1. **Plain tracker:** two standalone agent identities, dependency and hierarchy edits, competing claims, submission, attributable agent rejection/rework/acceptance, problem report; no workflow policy or team rows required.
2. **Optional policy:** same basic ticket flow plus independent plan/result review and delegated execution; no team run required. Late significant findings, failed checks and self-review block acceptance/start as appropriate.
3. **Managed team:** ready improver/coordinator, fresh exact-ticket worker, host registration/acknowledgement, independent validator, stop/recovery and capacity checks; no worker can take a second assignment in the same context/session.

Run `go test ./...`, `go vet ./...`, Windows build and Linux cross-build after integration. Use sandbox-approved Git subprocess execution if the current Windows runner cannot create signal pipes; record that limitation. Validate installed skill discovery in fresh host contexts and inspect actual SQLite records in a controlled smoke fixture, not the unapproved case study. Update the simple work board and record source/test evidence in `docs/testing/team-workflow-acceptance.md`.

Architecture approved by `layer_plan_review`; all four required amendments incorporated: preserve both journal payload generations, cover standalone unblock/milestone release, specify transactional helper boundaries and classify pending/historical managed identities, anchor standalone delegated authority to recorded policy and prevent shutdown fallback. Reviewer explicitly approved implementation after these amendments. L0 complete.
